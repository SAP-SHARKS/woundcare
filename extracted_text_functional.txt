WOUND CARE AI PLATFORM
Screen-by-Screen Functional Requirements
Functional behavior specification for UI/UX finalization and later development
How to use this documentEach screen is written as a self-contained mini-spec. You can paste one screen section into an AI design or coding tool without supplying the entire application. The UI mockup requirements document defines visual direction; this document defines what each screen must actually do.

Important clinical rule principleDo not hardcode thresholds such as age &gt; X, wound growth &gt; X%, necrotic tissue &gt; X%, assessment overdue &gt; X days, or urgent-review SLA &gt; X hours. Store them as versioned configuration controlled through authorized admin/clinical-governance screens.

Shared Functional Rules Across All Screens
Tenant isolationEvery patient, wound, assessment, image, alert, task, report, and configuration override must be resolved within the authorized organization context. Hiding a button is not sufficient authorization.

Shared admin-configurable concepts
Clinical thresholds: age, wound area change, tissue %, pain change, lab thresholds where approved.
Time windows: healing comparison period, overdue assessment interval, alert SLA, escalation timing.
Risk-factor weights and risk bands if a weighted model is used.
Reference lists: wound types, body locations, wound status, exudate, periwound findings, exposed structures, closure reasons.
AI settings: minimum confidence behavior, which outputs require calibration, which roles may approve.
Governance: global vs clinic override, approver role, effective dates, versioning.
Shared record-source principle
Keep original wound image separate from normalized/processed image.
Keep original AI output separate from clinician-approved final output.
Keep original finalized assessment version traceable after amendment.
Keep the rule version and input values that caused an alert.
