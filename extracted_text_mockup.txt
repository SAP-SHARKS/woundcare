WOUND CARE AI PLATFORM
UI/UX Mockup Requirements
Software screens only • Design exploration specification

Purpose of this documentUse this specification in different AI design tools to generate consistent high-fidelity software mockups. The goal is to finalize the visual system, information architecture, navigation, screen layouts, and clinician workflows before development. It intentionally excludes backend implementation, database setup, AI model development, production security configuration, and deployment.

Version 1.0  •  August 2026

1. Scope and Design Goal
Design the complete user interface for a modern AI-assisted wound-care management platform used by clinics, doctors, wound specialists, nurses, and administrators. At this stage, create high-fidelity UI/UX mockups only.
Do not build the backend in this phaseDo not focus on Supabase setup, production authentication logic, database migrations, APIs, model training, medical algorithm implementation, deployment, or infrastructure. The purpose of these mockups is to decide what the software should look like and how users should move through it.

Visual design and design system
Navigation and information architecture
Page layouts and content hierarchy
Clinical workflows
Desktop, tablet, and mobile behavior
Status treatments, alerts, tables, forms, cards, image framing, and AI review patterns
2. Product Overview
The platform helps healthcare organizations manage wound-care patients and track wounds longitudinally. The product must support multiple clinics while keeping each clinic’s clinical workspace conceptually separate.
Platform Super Admin
Manages clinics and top-level platform administration.
Clinic Admin
Manages one clinic, its staff, and operational settings.
Doctor / Wound Specialist
Reviews patients, wound progression, AI findings, urgent cases, and clinical assessments.
Nurse
Finds patients, captures wound photos, records assessments, and completes day-to-day clinical documentation.

Core clinical structure:
One patient may have multiple wounds.
Each wound has its own wound episode/profile.
Each wound may have multiple assessments over time.
Each assessment may contain wound photos, measurements, wound-bed information, exudate, periwound condition, pain, notes, and AI-assisted observations.
3. UI Design Principles
Premium modern healthcare SaaS, not an old hospital EMR.
Clean, calm, trustworthy, precise, and easy to scan.
Data-rich without feeling cluttered.
Strong hierarchy and generous whitespace.
Clinical information should be visually prioritized by importance, not displayed as equally weighted boxes.
Use color intentionally for status and interaction, not decoration.
Avoid generic Bootstrap dashboards, consumer wellness aesthetics, neon AI styling, cartoon medical art, giant gradients, excessive glassmorphism, and unnecessary charts.
Do not put every element in a separate rounded card. Use spacing, typography, sections, and dividers to create structure.
4. Design References and Color Experiments
The designer/AI will receive screenshots from other products as style references. These references are used to test different visual systems while keeping the wound-care product structure consistent.
Reference-image instructionUse attached screenshots for color palette, overall mood, typography personality, spacing, surface treatment, sidebar treatment, button design, card treatment, and component polish. Do not copy logos, branding, content, or exact layouts. Translate the aesthetic direction into the wound-care product while preserving the information architecture in this document.

Keep the same screen content when testing different palettes.
Do not redesign the underlying product structure just to match a reference.
Use a calm neutral frame around wound photographs because clinical images already contain reds, yellows, browns, blacks, pinks, and many skin tones.
Do not introduce unrelated accent colors unless needed for meaningful clinical status communication.
5. Clinical Status System
Improving
Positive status. Usually restrained green or another positive treatment.
Stable
Neutral state. Typically neutral blue/grey.
Needs Review
Attention required; typically amber.
Worsening
Concerning trend; stronger warning treatment.
Urgent / Critical
High-priority state. Use red sparingly and locally rather than filling entire cards.

Status should never rely on color alone. Combine color with a label, icon, border, or concise explanation.

8. Global Component and Interaction Requirements
8.1 Empty States
Use useful empty-state copy with a clear next action.
Example: “No active wounds. Create the patient’s first wound to begin tracking healing progress.”
Avoid large cartoon illustrations unless extremely subtle.
8.2 Loading States
Prefer skeleton rows, image placeholders, and subtle progress indicators.
Avoid generic spinning loaders across the whole application.
8.3 Modals and Drawers
Use side drawers for contextual viewing/editing when the user should remain in context.
Use full pages for clinically important workflows such as wound assessment and AI review.
8.4 Tables
Clear headers, restrained borders, generous row height, subtle hover states, contextual actions, and filters above the table.
Avoid excessive gridlines.
8.5 Cards
Use cards selectively for meaningful conceptual groups.
Do not wrap every piece of data in its own card.
Prefer whitespace, sections, typography, and dividers when possible.
8.6 Typography
Use a highly legible modern sans-serif such as Inter, Geist, SF Pro, or a comparable system.
Create clear hierarchy between page titles, section titles, primary clinical values, labels, supporting text, and metadata.
Clinical measurements should be immediately scannable, e.g., a large “4.1 cm²” with a smaller “Surface area” label.
9. Wound Photography and AI Visual Language
9.1 Wound Photography
Wound images are clinical evidence and should be framed neutrally.
The UI palette must not compete with reds, yellows, browns, blacks, pinks, and diverse skin tones in wound photographs.
Use calm neutral image backgrounds/borders and consistent image aspect treatment.
9.2 AI Visual Language
AI should feel integrated into clinical workflow, not like a separate chatbot.
Prefer labels such as AI-assisted analysis, Automated observation, AI measurement, Awaiting clinician review.
Do not use robots, holograms, glowing purple, sparkles, or futuristic AI styling.
Show explainability: which observation or rule caused a review flag.
Do not display arbitrary scores unless they have genuine clinical meaning.
10. Responsive Requirements
Desktop
Primary clinician/admin workspace optimized around 1440 px, with graceful behavior around 1024 px.
Tablet
Important for nurses and clinical review; maintain clear touch targets and simplified layouts.
Mobile
Patient search, patient overview, assessment, camera capture, AI review, alerts/tasks should have purpose-built mobile layouts, not merely a scaled desktop UI.
RTL readiness
Initial mockups may be English, but layouts should be capable of later Arabic/right-to-left support. Avoid designs that depend completely on left-to-right positioning.

Use larger tap targets on mobile.
Use sticky primary actions where appropriate.
Collapse tables into meaningful stacked rows/cards rather than forcing horizontal scrolling for core workflows.
Reduce secondary information while preserving clinical priority.

12. Initial Color / Style Test
Before designing all screens in every color direction, use a small representative set to compare palettes apples-to-apples.
Generate the Wound Care Command Center. It exposes sidebar, navigation, KPI treatment, lists, alerts, buttons, severity colors, and hierarchy.
Generate the Patient Overview. It tests dense clinical information, tabs, risk badges, patient identity, and wound cards.
Generate the Wound Profile / Healing Timeline. It tests whether the palette coexists with wound photography and longitudinal data.
Generate the AI Analysis Review. It tests image framing, measurements, AI findings, clinical review actions, and whether AI feels credible rather than gimmicky.
Comparison ruleWhen switching to a new color/style reference, keep the information architecture and sample content the same. Change only the visual system. This makes it possible to judge the palette itself instead of accidentally preferring a different layout.

13. Mockup Deliverables
Create high-fidelity mockups, not low-fidelity wireframes.
Create actual software product screens only. Do not create landing pages, marketing sections, pricing pages, or website hero sections.
Use realistic clinical sample content instead of lorem ipsum.
Maintain the same design system across all screens.
Maintain consistent sidebar, typography, buttons, inputs, tables, cards, badges, alerts, iconography, image framing, status treatments, spacing, and borders.
Show important empty, loading, warning, and review states where relevant.
Where practical, provide desktop and mobile versions of nurse-critical workflows.

Use any attached screenshots as inspiration for color, mood, typography, spacing, surface treatment, navigation style, cards, and component polish, but preserve the wound-care information architecture in this document. Create original software mockups only, not landing pages. The priority is exceptional clinical usability, clear hierarchy, calm visual design, and a premium modern SaaS experience.
